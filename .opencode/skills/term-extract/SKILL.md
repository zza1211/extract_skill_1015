# 海外技术条款抽取

## 目标与职责

从原文圈定能用于选型配置的设备或系统要求，输出原始定位标签。保留影响配置的关键参数，避免混入其他设备参数；少量不影响选型的冗余文字允许保留。产品分类仅作参考，不以分类正确率验收，也不因分类不确定就删除采购对象。

你负责最终判断。工具提供原文、定位与结构检查；辅助模型若以后接入，只能给候选建议。初版没有外部抽取模型工具，不要自行创建或调用未配置的服务。

开始任务时读取 [业务口径](references/business-rules.md)、[输出协议](references/output-format.md) 和 [输入与读取说明](references/input-format.md)。首次复盘、接收反馈或维护经验前读取 [经验记忆](references/experience.md)，其中有复盘的严格字段。日常抽取只召回相关的已发布经验，不读取私有案例库或历史运行。

## 执行流程

### 1. 注册和读取原文

使用 term_document_prepare，传入用户指定的输入路径和本次独立工作目录（建议 runs/任务名）。工具保留源文件，产生 index、manifest 和可读分片。真实输入缺少标签时不能自行补造定位；demo_tags 仅在用户明确进行演示时使用。

注册时固定本任务的已发布经验快照；空库也生成空快照。任务执行期间不因新发布或撤回切换经验版本。重跑、切换经验或迁移没有快照的旧任务时，使用新的工作目录注册，不能覆盖已有快照和回执。

同一个 text 字符串或表格单元格允许包含多个真实 Cxx 标签。注册工具按标签出现位置生成定位片段，并保留原块及表格行列；这不代表技术条款或设备已经拆分。不要因多个标签要求用户重写 JSON，也不要把整个字符串当成唯一可选起止范围。旧版索引需要重新 prepare。

使用 term_document_read 读取 index。优先完整读取紧凑原文，需要分页时沿 next_cursor 连续读取至 has_more=false；尽量批量读取，避免逐设备反复载入全文。每份文档用新会话。不要把 search 命中集合当成全文覆盖。

模型收到的是保留全部原文的紧凑视图：同一个段落或表格单元格只标一次位置，详细 parts 和覆盖偏移留在机器回执。不要要求读取整份 index 或所有 view 文件；那些是诊断资产，含重复机器元数据。

读取工具会记录实际交付的原文区间。超长单元格分片时，同一标签的所有部分都需要读取。若工具提示截断、原文未交付或上下文预算不足，先解决或明确报告未完成；不要依赖自动 compaction 改写原文。

### 2. 形成全篇候选

统一识别采购对象，再圈定各对象的连续片段，判断 normal、general、separate，查找采购数量来源。保留一份简短草稿：候选名称、拟定区间、关联对象、数量来源标签和具体疑点。无需给每个单元格写一份语义账本。

全文读完后先用 term_result_checkpoint 保存简短候选及未解决问题，再针对具体问题核验。候选可以不完备，保存不代表提交；不要为了在一次生成里想完所有问题而迟迟不写任何工作产物。每个候选只记录区间、归属、数量来源与疑点，不复述所有技术参数。

候选未保存或与当前 index 不匹配时，搜索工具会提示先保存候选；无需先解决所有疑点才能保存。不要通过查找历史 final 或未指定目录绕过这一阶段。

形成候选后，将具体疑点与错误类型交给 term_memory_recall，默认最多召回三条、约 6 KiB。相近疑点合并检索，不按每种设备重复调用。没有疑点无需为调用而调用；空库或无匹配时按原文判断。命中只表示相关，先核对适用条件和排除情况；经验不是原文事实、数量或边界答案，不能覆盖业务口径。工具记录的是实际交付的经验，不证明已采用或采用正确。

表格需要结合列标题、行名和合并关系判断归属。续表没有重复标题不意味着新产品；同名设备也不自动属于同一个采购对象。检查标题下多种规格、Indoor/Outdoor 子标题、系统软硬件组成和跨章节引用。

连续表格行、同一单元格的多个 C 标签，以及跨页续表，属于版式或定位切分，不能据此判为 separate。先判断业务上是否仍是连续规格。Wi-Fi 系统的并发/带宽等整体性能可成为 general；不得为规避区间表达问题而把它误标 separate，也不得把 AC 参数强行圈进 AP。

### 3. 围绕疑点核验

集中收集疑点，调用 term_document_read 补读边界邻域和关联片段；使用 term_document_search 查采购清单、设备别名、型号及显式引用。搜索结果 has_more=true 时仍有未展示命中，按需要继续读。

只搜索草稿中有具体问题的对象，避免全文读完后再按每类产品关键词重复扫描。已在全文确认的数量来源不必再次搜索；多个独立疑点可以在同一轮发起工具调用。可选 cursor、limit、max_bytes 可省略，工具运行时会补默认值。

数量单独取证，区分采购量、每站配置和总计，以及容量、端口数、连接数、冗余部件数。不能从“8 个虚拟防火墙”“两条上联”“双电源”直接推出实体设备采购量。

通用要求需有影响选型的技术内容及适用对象；分散片段需有同一采购对象的依据。特别核对清单中未匹配的对象、未归属的设备要求、孤立 general 和 separate 片段。名称提及的配套设备不自动成为独立采购项。

### 4. 校验与提交

按照输出协议生成七字段 JSON 数组，同时生成证据 sidecar。用 term_result_validate 提交 result_json 和 evidence_json。结果工具检查结构、标签、关联和重叠；对问题按原文修订，必要时补读。

证据以标签和简短归属说明为主，不把每个条款的技术参数重新写一遍。separate 需要同一采购对象与真实不连续区段的依据；收到 SEPARATE_LOCAL_LAYOUT_REVIEW 时复查连续行/续表，不能用“标签之间有别的设备”作为唯一解释。

结构通过后，仍要核对：目标产品是否漏抽；关键参数是否完整；是否混入其他设备参数；general/separate 是否关联正确；数量是否有原文依据。无需仅为重复确认而再次调用模型读整篇。

提交前由你基于本篇原文做一次简短复盘，与结果一起交给 term_result_commit 的必填 reflection_json。最多记录三条有真实 evidence_tags 支撑、可以迁移的观察：本次实际疑点、做过的核验动作或自我修正，以及对应标签。不要复述现有业务口径或已召回经验，不要复制设备数量，也不要把“通过了结构校验”当成成功经验。只保存简短事实与结论，不保存内部思维链。未发现新经验时传空 insights，并在 no_experience_reason 说明原因，不机械凑数。复盘使用当前会话已有判断，无需另调模型。

使用 term_result_commit 保存已核验草稿。工具会核对读取回执、输入版本和未解决事项；不满足条件时返回明确错误，修复后再提交。成功后保存不可变运行记录，返回 learning.run_id（下文简称 run_id）；复盘中的观察可形成带 source_ids 的未验证候选，它们不会进入生产召回。报告 run_id、结果路径与需复核的语义提示。达到预算上限时保留草稿并报告未完成，不把文字总结当成已提交结果。

检查 learning 状态：若 committed=true 但 learning.status=learning_failed，结果已经保存，学习归档或复盘尚未完成。明确报告该状态，按工具 next_action 重试或补齐，不声称候选已保存，也不编造 run_id。演示运行不进入经验库。

### 5. 接收反馈与补齐复盘

用户针对已提交结果给出反馈时，先调用 term_memory_feedback，传旧 run_id、用户反馈原话 feedback_text、必填 reflection_json，以及可选的 after_result_json。feedback_text 保留原话；after_result_json 是你整理的修正稿，在 confirm-feedback 前不能称为人工正确答案。区分用户指出的事实与你提出的修正，不能自行填写确认人或把反馈视为人工验收。

若第一次只保存原话、没有修正稿，形成完整修正稿后必须再次调用 term_memory_feedback：仍传同一旧 run_id、同一用户原话，增加完整 after_result_json 和本次复盘，取得新的 feedback_id。新提交不会自动补齐旧反馈。交给维护者确认的是新的带稿 feedback_id，旧反馈保留未确认；若首次已具备完整修正稿，可一次记录。

需要修正结果时，先保存反馈指向旧 run，再回原文取证、校验并重新提交，得到新 run_id。旧运行记录不得覆盖。若旧运行的复盘为 pending，且已有足够原文与结果可复核，可用 term_memory_reflect 补齐；材料不足时说明缺口，不编造观察。

## 可持续改进

本次抽取使用固定版本的口径与经验快照。主 agent 主动复盘，工具保存运行、反馈和候选；没有后台会话监听或自动从聊天中学习。空库的第一篇也可以留下新观察，但运行来源和反馈来源在人工确认前不能用于经验评测或发布。

日常抽取只使用 recall、feedback、reflect，不直接调用 propose、evaluate 或批准发布。维护者通过本地记忆工作台或 CLI 确认运行或纠正反馈后，term-memory-curator 可按 source_ids 整理候选与执行离线回归。成功来源允许保留已正确场景的评测，不要求制造错误；纠错来源仍需证明目标改善。发布和撤回仅由人工在工作台或 CLI 执行；agent 不调用工作台 HTTP 接口代替人工确认或发布。正常结果提交无需逐篇等待人工审批，来源确认也不等于批准泛化规则。

质量评测看产品召回、选型参数覆盖、其他设备参数混入、关联和数量；记录累计模型用量、耗时与人工纠错量。已参与经验归纳或提示修改的文档不能再当独立测试证据。
