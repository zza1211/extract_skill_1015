# 评测集准备与经验验证指南

日常使用建议走 **OpenCode 原生独立验证**：你准备标书原文、可信正确结果和案例族，Agent 负责生成两组抽取结果、比较并申请发布。**不需要你编写前端“离线评测清单 JSON”。**

网页中的路径框属于兼容的离线维护路径：读取已经生成的 baseline / candidate 输出和人工关键断言，不启动模型。两条路线都能留下评测记录，但准备材料和验证能力不同。人工审核发布则是第三条独立路径，可以不先评测。

## 一、先明确要评测什么

本项目的经验验证回答的是：**在同一模型、同一固定业务口径和正式经验基线下，加入某一条候选经验后，是否修复目标问题，而且没有破坏相关能力或误用到反例？**

它不是比较“模型 A 和模型 B 谁更强”，也不是只检查 JSON 格式。换模型、提示词和候选经验同时变化，就难以把变化归因于这条经验；需要另外组织整体方案对比。

业务质量按以下问题检查，产品分类暂不计对错：

| 维度 | 需要覆盖的情况 |
|---|---|
| 漏产品 | 所有目标设备或系统是否都有对应记录；光模块多规格是否拆分 |
| 关键参数遗漏 | 主体、通用要求及分散片段是否共同覆盖选型所需参数 |
| 参数污染 | 是否混入另一设备的参数，导致错误选型 |
| 数量 | 是否取对采购对象、单位、表格行与数量作用范围 |
| 关联与边界 | normal / general / separate 是否合适；通用约束和分散片段是否关联正确 |
| 排除与合并 | 机柜、布线、纯品牌准入是否排除；完整系统是否被错误拆散 |

边界与标签区间不完全相同，不必直接判错。少量无害说明可以保留；遗漏关键参数或多抽其他设备参数才是业务错误。连续表格中的两行也不因此成为 separate。

## 二、推荐路线需要什么文件

每篇案例准备一份原始解析 JSON 和一份可信正确的七字段结果。标签已按当前口径确认，且与输入使用同一套 Cxx，就可以导入，无需额外逐篇重复审核。

建议放在仓库外的私有目录：

```text
D:\私有数据\term-evaluation\
  campus-a\
    input.json
    labels.json
  campus-b\
    input.json
    labels.json
  office-c\
    input.json
    labels.json
  holdout-d\
    input.json
    labels.json
```

| 材料 | 含义 | 谁准备 |
|---|---|---|
| `input.json` | 带真实 Cxx 的完整 text / table 原文，与实际抽取输入相同 | 已有解析程序 |
| `labels.json` | 正确的完整七字段 JSON 数组，包含该篇所有目标设备 | 现有人工确认案例 |
| `family_id` | 相同模板、来源或近重复文档的分组名 | 你指定，Agent 可建议 |
| `split` | development、regression 或 holdout | 导入时指定 |
| 反例说明 | 此文档为何触及候选经验的适用或排除边界 | Agent 选择后说明；不清楚时再问人 |

推荐路线不用你预先生成 baseline / candidate，不用写 `assertions`，也不用手工建立文档索引。Agent 会调用文档工具和独立子会话完成。

`labels.json` 的字段与正式输出完全相同，例如：

```json
[
  {
    "id": 0,
    "条款标题": "Indoor Access Point",
    "条款分类": "normal",
    "相关条款": [],
    "产品分类": "WLAN AP",
    "定位标识": ["<C10>", "<C16>"],
    "产品数量": "12"
  }
]
```

示例仅说明格式；真实标签必须定位到对应 input 的原文，并覆盖整篇应抽设备，不能把一小段示意当成完整正确标签。分散条款沿用现有七字段协议，以多个 separate 片段及相关条款描述。

### 按文档家族划分，避免相似案例冒充独立验证

同一项目的修订版、译文、换校名套模板、近重复标书应属于同一 family。仅更改 `family_id` 不能产生独立性。独立案例应在原文和家族上都与经验来源独立。

| 数据用途 `split` | 作用 | 可否用于本轮经验归纳与晋级 |
|---|---|---|
| `development` | 从错误或成功中归纳候选经验，重现目标情形 | 可以 |
| `regression` | 检查其他案例是否退化，提供适用边界反例 | 可以验证，不能拿反例答案提示抽取子代理 |
| `holdout` | 最后评估一版整体方案的真实泛化效果 | 不参与日常经验归纳、反复调参或晋级 |

`split` 是案例的长期用途；`role` 是某次经验实验中扮演的角色，两者不是同一字段。一个 regression 案例可以在适合的实验中扮演回归或反例，但本次不能让同一原文同时充当两种角色。

已有上百篇时，可先按 family 分成大约 60% development、25% regression、15% holdout，再检查小类和典型结构是否覆盖。这只是启动建议，不是程序要求，也不必机械按篇数凑比例。相同家族不能跨组。

少量起步时，可以先用 5～10 篇不同家族完成学习和相关回归，另外保留一批从未用于归纳的测试案例。只有三篇也能试通流程，但不能据此宣称方案已经充分验证。

### 每条经验至少要哪些角色

| 实验角色 `role` | 选什么 | 最小要求 |
|---|---|---|
| `development` | 这条候选经验的真实归纳来源 | split 为 development；覆盖候选的全部来源原文 |
| `regression` | 可能被这条规则影响、原本处理正确的其他案例 | 与开发来源独立 |
| `counterexample` | 看起来类似、但不应套用规则或需排除的边界情形 | 写清 `scope_note`；与来源和本轮回归均为独立家族 |

回归和反例通常都以 `split=regression` 导入，再由 Agent 在本轮指定不同 role。推荐按规则的潜在影响范围逐步增加相关案例；“每种角色一篇”只是最小程序门槛。

例如候选经验是“从数量清单补充设备数量”，开发案例应确实存在同一设备的清单与技术章节；回归检查另一种数量布局；反例可以是清单里的 license 数量或 AP 管理容量，必须防止它被当成设备采购数量。拿一篇完全无关、根本没有数量场景的标书充当反例，通常没有验证价值。

## 三、实际操作：原生 OpenCode 路线

### 1. 先导入验证案例

网页“学习与案例 → 可信案例 → 导入案例”，填写 input、labels 的本机路径、family 和 split。导入只归档并校验材料，不启动模型。也可以在 OpenCode 明确要求导入可信案例。

开发篇可在标签学习时登记；准备独立回归与反例后，再让 Agent 继续实验。只给标签文件路径，不要把正确结果正文贴进负责盲抽的对话。

### 2. 新会话完成一篇标签学习

```powershell
opencode --agent term-extractor
```

可复制并替换以下提示词：

```text
请使用 term-extract 技能进行标签学习。

输入：D:\私有数据\term-evaluation\campus-a\input.json
正确标签：D:\私有数据\term-evaluation\campus-a\labels.json
案例族：campus-template-a

标签已按当前业务口径确认，且与输入使用同一套 Cxx。
先独立抽取、核验并提交，冻结首次预测后再查看标签。
基于原文和业务影响比较差异，总结有适用条件和排除条件的候选经验。

可信案例库已有独立 regression 案例。只对有价值的新候选组织验证：
覆盖其全部开发来源，选择相关独立回归和触及排除边界的反例，
使用原生 term-trial 子会话分别完成 baseline / candidate 抽取。
不足时保留候选并说明缺什么，不用无关案例凑数。
通过全部门槛后发布，报告 memory_id、revision、experiment_id、评测与发布状态。
```

每篇新学习用新会话，防止上一篇标签污染本篇盲抽。已经解封标签的学习可在原会话继续复盘和验证；不要在同一已知答案的会话重新做“首次盲抽”。

### 3. Agent 实际执行什么

```text
原文 + 私有可信标签
  → 主 Agent 先抽取、核验、提交
  → 冻结首次预测，再解封标签、比较差异
  → 生成候选经验（此时未生效）
  → 选择 development / regression / counterexample
  → 冻结固定业务口径、正式经验基线和候选版本
  → 每个案例各跑 baseline、candidate 两个独立 term-trial 子会话
  → 全部预测冻结后，主 Agent 才看到标签比较
  → 判断局部差异，必要时转人工待办
  → finalize 校验真实会话工件并重算评测
  → 通过后 publish；后续新任务可召回已发布经验
```

baseline 使用本次冻结的正式经验包；candidate 在相同条件下加入本条待验证经验。三个案例最少需要六个独立子会话，另有主 Agent 的首次抽取、比较和复盘开销。因此不是每完成一篇普通抽取都强制跑六次。

子会话只收到本票原文、固定规则和对应经验包，不收到正确标签、基线结果或父会话的修复提示。工具核查真实 OpenCode 导出记录、父子关系、模型/档位、允许的工具、原文完整读取和正式提交，不把“模型说自己跑过了”当成证明。

### 4. 怎样看通过或失败

候选保存、评测通过、正式发布是三件事。自动路径的核心门槛是：开发目标修复或保持正确，没有退化，独立回归和边界反例通过，来源与实验材料有效，且没有未解决的阻塞差异。

`fix_improvements` 表示本实验观察到修复；`success_cases` 也可能只是保持了原本正确，不能把“未退化”解释成准确率提升。区间不同的局部语义问题由 Agent 结合原文核验，不确定时进入待办；明确漏产品、污染、数量和关系错误不能靠“无害”意见抹掉。

网页“学习与案例”查看学习记录，“经验库”查看精确修订、评测和当前发布依据。材料不足时先补案例；待办需要判断时，在网页答复，再回原 OpenCode 会话要求继续。Agent 不得代人填写人工答复。

## 四、前端的“评测 JSON 路径”到底填什么

它指的是**离线评测 manifest 文件的绝对路径**，不是 input.json，不是七字段 labels.json，也不是任意一份输出结果。网页服务在本机读取这个文件，里面再引用已经准备好的索引、两组输出和断言。

| 路线 | 你需要准备 | 谁生成抽取结果 | 是否启动模型 |
|---|---|---|---|
| 推荐：OpenCode 原生验证 | 原文、可信完整标签、family、split | 独立 term-trial 子会话 | 是，由 OpenCode 调用当前模型 |
| 兼容：离线 manifest | 索引、已存在的 baseline/candidate、人工关键断言、来源记录 | 维护者提前生成 | 否，评测器只比较文件 |
| 人工审核发布 | 规则与来源证据、审核人和理由 | 不要求本次运行两组输出 | 否，独立人工发布依据 |

离线 manifest 的结构示例：

```json
{
  "schema_version": 1,
  "cases": [
    {
      "case_id": "example-case",
      "family_id": "example-family",
      "role": "fix",
      "split": "development",
      "confirmed_by": "示例维护者",
      "index_path": "document/index.json",
      "baseline_result_path": "baseline.json",
      "candidate_result_path": "candidate.json",
      "assertions": [
        {
          "object_key": "Indoor AP",
          "anchor_tag": "<C10>",
          "required_tags": ["<C10>", "<C12>", "<C16>"],
          "forbidden_tags": ["<C20>"],
          "quantity": "12",
          "clause_category": "normal"
        }
      ]
    }
  ]
}
```

这只是单案例格式示意，不满足完整发布所需的回归和反例门槛；不要直接用于真实经验。离线 `role` 使用 `fix / success / regression / counterexample`，与原生工具的 `development` 角色命名不同。

### 完整 labels 和 required / forbidden 断言有何区别

完整 labels 描述整篇应该抽出哪些对象及其区间、关系、数量。原生比较以这些标签为依据检查对象和差异，再处理区间的业务含义。

离线断言只挑出每个设备的关键定位：

- `anchor_tag` 唯一对应设备主体；`required_tags` 是不能丢失的参数，必须包含 anchor。
- `forbidden_tags` 是不得混入的其他设备参数；不是把每个标签区间之外的文字都视为错误。
- `quantity` 和 `clause_category` 可进一步约束数量与主体分类。

例如正确范围是 C10～C16，实际范围 C10～C17 多了一句不影响选型的维护说明，仍可能通过；若少了 required 的 C16，或混入 forbidden 的另一个设备 C20，就失败。程序按原文顺序解析区间，不按 C 数字排序。

**只写一个 AP 断言，不能据此证明整篇没有漏交换机。** 离线评测不会从原文自动发现未列入断言的目标设备；要覆盖漏项，必须把应抽对象及其关键参数都写进断言。完整标签也不等于已经给每个原文标签标注了“关键参数”语义，两者服务的比较方式不同。

### 可运行的合成 example

仓库的 [examples/evaluation](../examples/evaluation/README.md) 提供三个不同家族的合成案例、完整七字段标签、baseline / candidate、清单模板和隔离准备脚本。每组还有 `annotations.json`。它用于理解格式、尝试网页按钮和观察报告，不调用模型，也不代表真实抽取效果。

在仓库根目录运行：

```powershell
# 默认生成到系统临时目录
python -X utf8 examples/evaluation/prepare_demo.py

# 或指定仓库外的空目录；二选一即可
python -X utf8 examples/evaluation/prepare_demo.py --out-dir 'D:\私有数据\term-eval-demo'
```

脚本只准备材料，不自动评测或发布。它生成 `evaluation.manifest.json` 和 `demo-info.json`，输出的 `demo_root`、`memory_id`、`revision`、`manifest_path` 对应同一个隔离演示库；同时打印 `evaluation_command` 和 `ui_command`。

复制打印的 `ui_command` 启动演示网页，在演示候选中填写 `manifest_path`；或复制 `evaluation_command` 只看终端报告。静态的 `manifest.example.json` 用来阅读字段，运行后生成的 `evaluation.manifest.json` 才引用实际准备好的索引。

**只在该演示库启动的网页上使用示例清单**，不要选生产经验来套演示输出；真实候选的开发案例必须来自它自己的归纳来源，来源哈希与家族均会检查。若同时运行日常工作台，按示例 README 使用不同端口，确认页面显示的项目和库路径确实指向演示目录。

没有必要为了走推荐路线先填写这个框。已有真实 input / labels 时，优先导入可信案例并让 OpenCode 组织原生验证。

离线字段、来源确认、路径解析与门槛详见 [memory-evaluation.md](../.opencode/skills/term-extract/references/memory-evaluation.md)。

## 五、建议你现在如何开始

1. 选一篇已有人确认标签、且确实有典型难点的文档做 development，先跑一次标签学习，查看产生的候选是否具体、可迁移。
2. 根据这条候选的触发条件，从其他家族选择相关回归和边界反例；两者作为 regression 导入，保留未使用的 holdout。
3. 让 OpenCode 执行独立验证，记录失败原因、实际 token / 时间和需要人工判断的地方；不要通过删断言或换成无关案例来追求通过。
4. 发布后用新的标书观察真实消费；阶段性在未参与学习的 holdout 上评估整套方案。holdout 一旦用于归纳或反复调参，就不再把它声称为最终保留测试。

人工已明确认可某条规则、暂时又缺验证案例时，可以走“人工审核发布此版本”；页面如实显示“人工审核发布／未评测”。这与自动评测发布并行，既不伪造通过记录，也不强迫每条人工规则先支付六次抽取成本。
